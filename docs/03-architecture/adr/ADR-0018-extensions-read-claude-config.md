# ADR-0018 Окно «Расширения»: список плагинов и магазинов у Claude Code, состав и серверы MCP из файлов без секретов, запись только вызовом `claude plugin`

> Решения составителя по Issue #59 (2026-10-30), не согласованы: открытые решения - D-01, D-02, D-04..D-09, D-12 фичи 14. Проверено живьём в Claude Code 2.1.314
> в изолированном `CLAUDE_CONFIG_DIR` и по документации code.claude.com. Опирается на ADR-0002 (изоляция интерфейса), ADR-0005 (читающие команды), ADR-0003 (сессии запускает Claude Code).

## Decision Drivers

- Что получит сессия, решает Claude Code по каталогу запуска и нескольким файлам настроек; Cyborg не подменяет Claude Code (ADR-0003) и не должен расходиться с ним в понимании «включено».
- Есть машиночитаемые `claude plugin list --json` и `claude plugin marketplace list --json`; у `claude mcp list` и `claude plugin details` JSON нет.
- Конфиги серверов MCP хранят ключи в `env`, `headers` и аргументах запуска; `claude mcp list` печатает аргументы и запускает серверы.
- Установка плагина запускает чужой код с правами пользователя; магазин может объявить команду установки.
- Интерфейсу не доверяют: аргументы каналов и пути проверяет главный процесс (ADR-0002).

## Context

Сессия Cyborg - `claude` с `cwd` в репозитории проекта и `--add-dir` для остальных его репозиториев (`src/main/sessions.ts`, `src/main/claude-args.ts`). Claude Code делит расширения на области `user`, `project`, `local`, `managed` (а также `session`, `synced`). Проверено: `claude plugin list --json` отдаёт все установки машины независимо от каталога запуска, а `enabled` считает для каталога запуска; `marketplace remove` удаляет и плагины магазина; установка с командой магазина без `-y` отказывает в неинтерактивном режиме; из `--add-dir` подхватываются скиллы, команды, агенты и ключи `enabledPlugins`, `extraKnownMarketplaces`, но не `.mcp.json`.

## Decision

1. Список магазинов и плагинов берётся у Claude Code: `plugin marketplace list --json` один раз и `plugin list --json` вне репозиториев и по разу в каждом репозитории проекта (не больше четырёх разом); установки `project` и `local` фильтруются по `projectPath` на репозитории проекта. Вывод разбирается по именам полей, неизвестные игнорируются. Запуск - `$SHELL -lc 'exec claude "$@"'`, как у сессий. Проверка: `test/extensions.test.ts`. Источник: D-03.
2. Состав плагина и скиллы читаются из файлов (`installPath` плагина, `.claude-plugin/marketplace.json` клона магазина, `~/.claude/skills`, `<репо>/.claude`): только frontmatter `name` и `description` из первых 8 КиБ, с пределами по числу и размеру; относительный путь плагина не выходит из клона. Проверка: `test/extensions-read.test.ts`. Источник: FR-14013.
3. Серверы MCP читаются из файлов, и в интерфейс уходят имя, транспорт и подпись (программа без аргументов либо схема и хост); `env`, `headers`, аргументы и путь адреса отбрасываются при разборе. `claude mcp list` вызывается только кнопкой, его вывод сохраняется как имя, состояние и причина. Проверка: `test/extensions-read.test.ts`, `test/extensions.test.ts`. Источник: D-04.
4. Cyborg сам не пишет в файлы Claude Code. Действия - вызовы `claude plugin install|uninstall|marketplace add|marketplace remove` с явной областью, в каталоге репозитория для `project` и `local`; `-y` и `--accept-command` не передаются; ответ берётся из итоговой JSON-строки `--json`. Одно действие за раз. Проверка: `test/extensions-act.test.ts`. Источник: D-09..D-11.
5. Аргументы каналов проверяет главный процесс: форма действия и имён (не начинаются с «-»), область, каталоги из разрешённых (`AllowedPaths`), число каталогов. Проверка: `test/extensions-act.test.ts` («обработчики каналов расширений»). Источник: ADR-0002.
6. Хабы - файл `hubs.json` в папке настроек (единственный новый файл Cyborg), общий для воркспейсов; хаб читается по https без учётных данных, до 1 МиБ, 500 записей, 10 с, источники только `github`, `git`, `url`. Проверка: `test/hubs.test.ts`, `test/static-guards.test.ts` (перечень пишущих файлов). Источник: D-07, D-08.

## Consequences

- Positive: окно согласуется с Claude Code в вопросе «включено ли»; секреты серверов не попадают в интерфейс; установка не обходит подтверждение чужой команды; зависимость от формата файлов ограничена составом плагина и серверами MCP.
- Negative: каждое открытие окна - несколько запусков `claude` (около 0,8 с на двух репозиториях); без `claude` в `PATH` магазины и плагины не видны; одобрение серверов `.mcp.json` выводится из нескольких файлов и может расходиться с Claude Code; состав удалённых плагинов виден только после установки.
- Risks: формат вывода `claude plugin ... --json` может измениться (разбор терпит неизвестные поля, но не переименования); подхват `--add-dir` для плагинов взят из документации, а не из живой сессии; хаб по https доверяет его владельцу в том, что он называет магазины (подключает их человек).

## Alternatives Considered

- **Читать `installed_plugins.json` и `enabledPlugins` напрямую.** Pros: без запуска `claude`. Cons: формат не обещан, слияние настроек и приоритет областей пришлось бы повторять. Why rejected: D-03.
- **`claude mcp list` при каждом открытии.** Pros: истинное состояние серверов. Cons: запускает программы серверов, ходит по сети, печатает их аргументы. Why rejected: D-04.
- **Писать `settings.json` самим для установки.** Pros: быстрее, без `claude`. Cons: дублирует логику Claude Code (скачивание, кэш, проверки). Why rejected: ADR-0003.
- **Передавать `-y` при установке.** Pros: установка всегда проходит. Cons: чужая команда выполняется без глаз человека. Why rejected: D-10.
- **Скачивать удалённые плагины ради состава.** Pros: полный список скиллов. Cons: сеть и место ради просмотра. Why rejected: D-06.
- **Хранить хабы в файле воркспейса.** Pros: переносятся вместе с ним. Cons: магазины Claude Code принадлежат пользователю, а не воркспейсу. Why rejected: D-07.
