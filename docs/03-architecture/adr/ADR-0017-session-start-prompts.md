# ADR-0017 Промпты кнопок запуска сессий: поле `prompts` файла воркспейса, подстановки только из проверенных значений, негодная запись не заменяется молча

> Решения составителя по Issue #31 (расширение объёма, 2026-10-27), не согласованы: открытые решения - D-17..D-21 фичи 12. Опирается на
> ADR-0014 (файл воркспейса), ADR-0015 (набор кнопок и его правка) и ADR-0002 (изоляция интерфейса).

## Decision Drivers

- Отзыв технического директора: «для любых кнопок писать промпт», «описания и кнопки видеть в конфиге». Кроме полосы команд, промпты зашиты в код у кнопок
  «Ревью», «Доработать», «CI» (`mrPrompt`), «Взять в работу» (`taskPrompt`) и сессии по задаче Jira (`jiraPrompt`).
- Эти промпты намеренно собирались только из проверенной ссылки или ключа: название, ветки и автор MR и задач - чужой текст и в запрос к модели не попадают.
- Файл воркспейса уже хранит настройки (ADR-0014, ADR-0015); интерфейсу не доверяют (ADR-0002).
- Без записи в файле поведение не должно измениться.
- Безмолвных fallback нет: негодная настройка не должна оставаться незамеченной.

## Context

Первое сообщение сессии собирает главный процесс: `session:create` вызывает `validateSessionStart` (`src/main/mrs.ts`), он по аргументу выбирает
`mrPrompt`, `taskPrompt` или `jiraPrompt` и отдаёт текст в `claudeArgs` позиционным аргументом (до `--add-dir`). Файлом воркспейса владеет `ProjectStore`;
поле `commands` читается и пишется отдельным каналом (ADR-0015).

## Decision

1. Поле `prompts` файла воркспейса - объект `{ "<id>": { "text", "description"? } }` с id `mr.review`, `mr.rework`, `mr.ci`, `task.start`, `jira.start`. Встроенные
   тексты (`DEFAULT_PROMPTS`) равны прежним, без записи в файле отправляется тот же текст. Проверка: `test/prompts.test.ts` («встроенные»), существующие тесты
   `mrPrompt`, `taskPrompt`, `jiraPrompt`. Источник: Issue #31; D-17.
2. Подстановки - только из проверенных значений и свои у каждого id: `{mr_url}`, `{task_url}`, `{status_command}`, `{jira_key}`. Название, описание, ветки и автор не
   подставляются. Неизвестная подстановка (опечатка либо чужая) - ошибка; фигурные скобки не из идентификатора остаются как есть; подстановка за один проход.
   Проверка: `test/prompts.test.ts` («разбор поля prompts», «подстановка»). Источник: D-18; комментарии к `mrPrompt`, `taskPrompt`, `jiraPrompt`.
3. Пределы: непустая строка до 2000 знаков в одну строку без управляющих символов, не начинается с «-» (позиционный аргумент `claude`); описание до 400 знаков;
   лишнее поле называется. Проверка: `test/prompts.test.ts`. Источник: D-21; `claudeArgs`.
4. Негодная запись при чтении (файл правили руками) не заменяется встроенной молча: `validateSessionStart` бросает ошибку с причиной, и сессия по кнопке не
   стартует (`newSession` показывает ошибку окном сообщения без обёртки Electron, `ipcErrorText`), записи других промптов не мешают; при сохранении любая проблема - отказ. Проверка: `test/prompts.test.ts`,
   `test/ipc-error.test.ts`, `scripts/smoke.mjs`. Источник: D-19.
5. Файлом по-прежнему владеет `ProjectStore`: `loadPrompts` и `savePrompts` читают и пишут только поле `prompts`, запись проектов и кнопок команд его сохраняет
   (общий перечень полей `OWN_FIELDS`), повреждённый и не прочитанный файл не затирается. Каналы `prompts:load` (поле как записано) и `prompts:save` (текст
   редактора, проверка заново в главном процессе, `savePromptsText`). Проверка: `test/prompts.test.ts` («ProjectStore: промпты в файле воркспейса»). Источник: ADR-0014 п.4; D-17, D-20.
6. Правка - пункт «Воркспейс → Промпты кнопок…» со своим диалогом Monaco, код редактора общий с кнопками команд (`initConfigEditor`): действующий набор целиком (встроенные с описаниями,
   записи файла на своих местах, лишние в конце), сохранение пишет текст как есть (по образцу ADR-0016 п.6). Проверка: `test/prompts.test.ts`, `test/menu.test.ts`,
   `scripts/smoke.mjs`. Источник: D-20.

## Consequences

- Positive: все промпты кнопок настраиваются в одном месте и видны с описаниями; чужой текст по-прежнему не попадает в запрос; опечатка в подстановке и негодный
  файл названы, а не уходят модели; поведение без записи в файле прежнее.
- Negative: файл воркспейса получает ещё одно поле; сессия по кнопке с негодной записью не стартует, пока файл не исправят; у самих кнопок списков подсказок с
  описаниями нет (описания видны только в редакторе); сохранённая копия встроенного промпта не получает правок текста в новых версиях.
- Risks: файл воркспейса, взятый из чужого источника, задаёт первое сообщение сессии (доверие к файлу то же, что у кнопок команд: его пишет сам человек или его
  команда); слеш-команда `mr.review` по умолчанию требует плагина dex-auto (как и раньше).

## Alternatives Considered

- **Отдельный файл промптов в `userData`.** Pros: не раздувает файл воркспейса. Cons: второй формат и второе место правки, не переносится с воркспейсом. Why rejected: D-17.
- **Массив `{label, text}`, как у `commands`.** Pros: единый формат. Cons: у этих кнопок нет подписи, место в коде называет id; порядок и повторы не нужны. Why rejected: D-17.
- **Произвольные id.** Pros: проще формат. Cons: опечатка в id молча ничего не меняла бы. Why rejected: D-17.
- **Подстановка названия, описания и автора.** Pros: богаче промпты. Cons: чужой текст попал бы в запрос к модели - то, от чего эти промпты защищены. Why rejected: D-18.
- **Тихая подмена негодной записи встроенным текстом.** Pros: сессия стартует всегда. Cons: человек не знает, что его правка не действует. Why rejected: D-19.
- **Один диалог для `commands` и `prompts`.** Pros: один пункт меню. Cons: два поля разной формы в одном тексте. Why rejected: D-20.
- **Подсказки с описаниями на кнопках списков MR и задач.** Pros: описание видно там, где кнопка. Cons: интерфейсу пришлось бы держать и перечитывать промпты. Why rejected: D-20 (отложено).
