# ADR-0019 MCP-сервер Cyborg для сессий: Streamable HTTP на 127.0.0.1, токен сессии в файле конфига, ввод в чужую сессию только в состоянии «ждёт»

> Решения по цели `mcp-session-tools` (2026-11-07) и ответам оператора (D-11, D-12 фичи 15); решения составителя, выведенные из кода правки, - D-04, D-06, D-14, D-15 фичи 15, не согласованы; закрытие вкладки (п.9) - просьба оператора 2026-11-09 и решения составителя D-18..D-20 фичи 15, не согласованы. Опирается на ADR-0003 (сессия - нативный CLI, наблюдение через хуки) и ADR-0002 (недоверенный интерфейс).

## Decision Drivers

- Сессия остаётся нативной (ADR-0003): инструменты добавляются через механизм MCP самого Claude Code, ввод в чужую сессию идёт её pty, как с клавиатуры.
- Инструмент должен знать, какая сессия его вызвала: от этого зависят проект, перечень каталогов и запрет писать себе.
- Порт на `127.0.0.1` и командная строка процесса видны всем пользователям машины; страница браузера дотягивается до `127.0.0.1`.
- Enter в сессии, стоящей на запросе разрешения, отвечает на этот запрос.
- Интерфейс недоверен (ADR-0002 п.5), а промпт новой сессии уходит аргументом `claude`.

## Context

Cyborg запускает каждую сессию сам (`$SHELL -lc 'exec claude --settings "$CYBORG_SETTINGS" "$@"'`) и знает её состояние только по событиям хуков в файле событий (ADR-0003 п.3, п.4). Claude Code подключает MCP-серверы ключом `--mcp-config` и умеет транспорт Streamable HTTP с заголовками. ADR-0002 отверг локальный HTTP-сервер для связи интерфейса с главным процессом; здесь сервер служит другой стороне - процессам `claude`, у которых IPC Electron нет.

## Decision

1. Главный процесс держит MCP-сервер Streamable HTTP только на `127.0.0.1`, порт выдаёт ОС; `POST /mcp` несёт одно сообщение JSON-RPC, методы - `initialize`, `ping`, `tools/list`, `tools/call`; потока SSE нет, `GET` - 405. Сервер не поднялся - сессии запускаются без него. Проверка: `test/mcp.test.ts`, `src/main/sessions.test.ts` («без MCP»). Источник: цель (D-01), инженерный вывод (D-15).
2. Каждая сессия получает свой токен: конфиг сервера с заголовком `Authorization: Bearer` пишется файлом 0600 в каталог файлов событий, путь передаётся переменной `CYBORG_MCP` и ключом `--mcp-config "$CYBORG_MCP"` перед прочими аргументами (за вариадическим ключом всегда стоит следующий ключ). При выходе сессии файл удаляется, токен отзывается; при старте Cyborg файлы неживых экземпляров удаляются вместе с файлами событий. Токен в аргументы командной строки не пишется. Проверка: `src/main/sessions.test.ts` («конфиг сессии в файле 0600», «убирает конфиги MCP убитого экземпляра»). Источник: цель (D-02).
3. Запрос с заголовком `Origin` отвергается 403, без известного токена - 401; токен называет вызывающую сессию, и инструменты действуют только над сессиями с тем же набором каталогов запуска. Проверка: `test/mcp.test.ts` («без токена… - 401; с Origin браузера - 403»), `src/main/sessions.test.ts` («соседи - сессии с теми же каталогами»). Источник: цель (D-03), инженерный вывод (D-06: главный процесс проектов сессий не знает).
4. Промпт `open_session` не проходит через интерфейс: интерфейс получает одноразовый ключ, номер вызывающей сессии и каталог, открывает вкладку вызовом `session:create` со стартом `{handoff}`, а главный процесс отдаёт промпт по ключу при совпадении каталога. Вкладка открывается в фоне. Нет ответа 20 с - ошибка инструмента. Проверка: `test/session-tools.test.ts` («Handoffs»); открытие в фоне - осмотр `src/renderer/app.ts`. Источник: цель (D-05, D-14), инженерный вывод (D-04).
5. В чужую сессию Cyborg пишет только в состоянии `waiting`, которое ведёт по хукам (`SessionStart`, `UserPromptSubmit`, `PostToolUse` главной модели, `Stop` без фоновых задач и расписаний, `Notification` ожидания человека): текст - одной записью в режиме вставки (bracketed paste), Enter - отдельной записью через 150 мс; перед каждой записью состояние перепроверяется, вышедшая из `waiting` сессия Enter не получает. Сессии в `starting` и `asking` не пишется ничего. Проверка: `src/main/sessions.test.ts` («SessionManager.say…», «сессия начала ход между вставкой и Enter - Enter не отправлен»). Источник: цель (D-07, D-09).
6. Работающей сессии сообщение ставится в очередь главного процесса в памяти и отдаётся по одному, когда сессия в `waiting` и 2 с без событий. Проверка: `src/main/sessions.test.ts` («работающей сессии - в очередь», «после события сессия должна помолчать»). Источник: цель (D-08); риск потери очереди с вкладкой принят оператором (D-12).
7. Подтверждения отправки в интерфейсе Cyborg нет: каждый вызов инструмента подтверждает человек запросом разрешения Claude Code в вызывающей сессии. Проверка: осмотр - у `send_to_session`, `open_session` и `close_session` нет окна Cyborg на пути от вызова до записи или закрытия. Источник: ответ оператора (D-11).
8. Текст инструментов проверяется до записи: ведущие «!» (оба инструмента), «-» (промпт), «/» и «#» (сообщение) отвергаются, управляющие символы сообщения вычищаются, предел - 100 000 байт. Проверка: `test/session-tools.test.ts` («validateOpenSession», «validateSend», «cleanMessage»). Источник: цель (D-10).
9. `close_session` закрывает вкладку проекта тем же путём, что крестик: главный процесс шлёт интерфейсу событие `session:close`, без окна завершает процесс сам. Соседку, которая работает, ждёт человека или запускается, инструмент закрывает только с `force: true`; свою вкладку сессия закрывает через 1 с после ответа. Проверка: `test/session-tools.test.ts` («validateClose», «close_session закрывает соседку сразу, а свою вкладку - после ответа»); снятие вкладки - осмотр `src/renderer/app.ts`. Источник: просьба оператора 2026-11-09, инженерный вывод (D-18, D-19, D-20 фичи 15).

## Consequences

- Positive: сессия поручает работу соседней вкладке и читает её итог без участия человека в переносе текста; токен не виден в списке процессов; Enter Cyborg не отвечает на запрос разрешения, о котором хук уже сообщил.
- Negative: состояние известно только по хукам - запрос разрешения, появившийся раньше своего `Notification`, Cyborg не видит, и сообщение в этом окне может уйти (D-12); сообщения в очереди пропадают с вкладкой и с выходом Cyborg; недоставленное из очереди сообщение снимается молча; сессии, запущенные до того, как сервер слушает, остаются без инструментов.
- Risks: смена формата событий хуков либо транспорта MCP в Claude Code ломает инструменты без изменения в Cyborg; если человек набирает текст в той вкладке, сообщение допишется к его вводу.

## Alternatives Considered

- **Токен в аргументе командной строки или в URL конфига в аргументе.** Pros: без файла. Cons: командную строку видят все пользователи машины. Why rejected: D-02.
- **Поток SSE.** Pros: полный транспорт Streamable HTTP. Cons: серверу нечего слать клиенту. Why rejected: D-01.
- **Промпт новой сессии через интерфейс.** Pros: проще канал. Cons: текст модели дошёл бы до аргументов `claude` через недоверенный интерфейс. Why rejected: D-04, ADR-0002 п.5.
- **Запись в работающую сессию сразу.** Pros: без очереди. Cons: Enter попал бы в её запрос разрешения. Why rejected: D-07.
- **Доставка из очереди сразу по `Stop`.** Pros: быстрее. Cons: чужой Stop-хук может продолжить ход. Why rejected: D-08.
- **Окно подтверждения отправки в Cyborg.** Pros: человек видит текст до отправки. Cons: второе подтверждение того же вызова. Why rejected: ответ оператора (D-11).
- **Распознавание запроса разрешения по выводу терминала.** Pros: закрыл бы окно до `Notification`. Cons: хрупко, вывод меняется с версией CLI. Why rejected: ADR-0003 (разбор вывода отвергнут), D-12.
