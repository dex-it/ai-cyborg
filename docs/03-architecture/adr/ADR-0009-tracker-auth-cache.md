# ADR-0009 Проверка входа в трекеры - один результат главного процесса, прогретый при старте и сбрасываемый по «Обновить»

## Decision Drivers

- `glab auth status` стоит около 1 с и шёл последовательно перед каждой выборкой задач и MR (brief perf, «Замер»).
- Результат проверки входа переиспользуется между обновлениями и сбрасывается сохранением настроек и «Обновить»
  (brief perf, «Требования» п.4).
- Задачи на Upcore - не дольше 0,8 с прогретыми и 1,8 с после «Обновить»; MR - 2 с до списка (SRS фичи 01,
  NFR-1004; SRS фичи 02, NFR-2002).
- Хосты GitLab, на которых выполнен вход, задают классификацию remote (ADR-0007 п.4).

## Context

Задачи и MR разбирают источники одним разбором (D-23 фичи 02): хосты и пользователи из `glab auth status`, логин из
`gh api user`. До правки каждая выборка проверяла вход заново, перед чтением remote.

## Decision

1. Главный процесс держит один результат проверки входа на трекер (GitHub, GitLab), общий для выборок задач и MR;
   хранится промис проверки с момента её старта, поэтому одновременные выборки ждут одну проверку в полёте
   (внешний источник: brief perf п.4; инженерный вывод - промис). Проверка: две выборки подряд дают один вызов
   `auth status` и один `api user`.
2. Переиспользуется любой исход - вход, «не залогинен», отказ, - без срока жизни (внешний источник: brief perf п.4
   называет только сбросы п.3). Проверка: после отказа проверки следующая выборка `auth status` не вызывает.
3. Сбрасывают результат «Обновить» - признаком новой проверки в аргументах `tasks:list` и `mrs:list` - и сохранение
   настроек в обработчике `trackers:save` главного процесса; результат проверки, начатой до сброса, не сохраняется
   (внешний источник: brief perf п.4; инженерный вывод - где делается сброс). Проверка: после сохранения настроек и
   после выборки с признаком следующая выборка вызывает `auth status`; открытие, вкладка, фильтр, проект - нет.
4. Проверка включённых трекеров запускается один раз при готовности приложения, до открытия окна панели; опроса по
   таймеру нет (внешний источник: решение владельца 2026-10-23 (а), D-22 фичи 01). Проверка: проверка запущена до
   первого списка, открытие после неё не вызывает `auth status` и `api user`.
5. После сброса выборка идёт по прежнему результату параллельно с новой проверкой; новая проверка изменила хосты с
   входом, их пользователей либо состояние входа - выборка выполняется заново по ней и её ответ заменяет первый,
   изменился только текст ошибки - первый ответ остаётся; прежнего результата нет - выборка ждёт проверку (внешний
   источник: решение владельца 2026-10-23 (б), D-23 фичи 01; инженерный вывод - сравнение без текста ошибки).
   Проверка: при «Обновить» вызов списка стартует до завершения новой `auth status`; сменившийся пользователь
   GitLab либо логин `gh` дают перестроенную выборку.
6. Проверка входа и чтение remote репозиториев идут параллельно (инженерный вывод: друг от друга не зависят).
7. Окно «Настройки» проверяет вход заново при каждом открытии и результат выборок не трогает (внешний источник:
   цель `panel-load-perf`, критерий 16; SRS фичи 01, FR-1009).

## Consequences

- Positive: открытие панели и вкладки не ждёт проверки входа; «Обновить» не добавляет её к критическому пути, если
  вход не менялся.
- Negative: вход, выполненный в терминале, списки видят только после «Обновить» или сохранения настроек; при
  сменившемся входе выборка после «Обновить» идёт дважды.
- Risks: окно «Настройки» и списки могут кратко показывать разное состояние входа.

## Alternatives Considered

- **Проверка перед каждой выборкой (прежняя схема).** Pros: состояние входа всегда свежее. Cons: около 1 с на каждое
  открытие. Why rejected: NFR-1004, brief perf п.4.
- **Ждать новую проверку после сброса.** Pros: выборка один раз. Cons: 1 с на «Обновить». Why rejected: предел 1,8 с
  после «Обновить» (п.5).
- **Отдельный канал `trackers:recheck` перед списком.** Pros: аргументы списка не меняются. Cons: два вызова и опора
  на их порядок. Why rejected: п.3.
- **`glab auth status --hostname <хост>` по хостам remote.** Pros: 0,65 с против 1,04 с. Cons: классификация remote
  строится по всем хостам входа, вид «нет remote / вход не выполнен» сменился бы. Why rejected: ADR-0007 п.4.
- **Без проверки при старте.** Pros: нет вызова без действия пользователя. Cons: первое открытие ждёт проверку. Why
  rejected: решение владельца (п.4); однократный вызов - не фоновый опрос (FR-1006).

## Расхождения с текущим кодом

Расхождений нет.
