# ADR-0013 Jira через jira-cli и сводка статуса проекта

> Решение составителя по запросу владельца (2026-10-26: кнопка статуса GitHub, GitLab и Jira, просмотр задач Jira, реакция агента),
> не согласовано: открытые решения - D-02..D-13 фичи 11. Расширяет ADR-0007: трекеры кода читаются через `gh` и `glab`, Jira - через
> `jira-cli`.

## Decision Drivers

- Разработчик узнаёт состояние работы обходом трёх мест (CI, MR, Jira); сводка нужна в окне (BR-005).
- Cyborg не хранит секреты и не пишет в трекеры (BRD продукта, non-goals; ADR-0007).
- Вход в Jira у разработчиков DEX уже настроен для `jira-cli` (мод dex-jira-tracker каталога ai-kit); второй способ входа не нужен.
- Сервер Jira блокирует учётную запись, которой снова и снова присылают неверные учётные данные.

## Context

У Cyborg есть трекеры кода через `gh` и `glab` (ADR-0007, ADR-0009), выборка MR с деталями (ADR-0008) и старт сессии из задачи либо MR с
начальным промптом из проверенной ссылки (ADR-0003, п.9). Jira у него не было: диалог проекта нёс неактивную галочку. Мод
dex-jira-tracker читает Jira через `jira-cli` и сверил формы его вывода на jira-cli 1.7.0 и Jira Server 9.2.

## Decision

1. Jira читается только `jira-cli`, процессом `jira` (`execFile`, массив аргументов, без оболочки, `cwd` - каталог данных приложения),
   командами: `version` и `me` (проверка), `issue list -q <JQL> --raw --order-by updated --paginate 0:50 [-p <проект>]` (мои открытые
   задачи: `assignee = currentUser() AND statusCategory != Done`), тот же список с `--plain --no-headers --columns key` и JQL
   `... statusCategory = "In Progress"` (ключи «в работе», потому что в `--raw` списка категории статуса нет), `issue view <ключ> --raw
   --comments 3` и `open <ключ> --no-browser` (адрес). Запись в Jira командами не делается. Предел вызова - как у `gh` и `glab`
   (120 с, 64 МБ).
2. Конфиг и токен `jira-cli` Cyborg не читает, не хранит и не передаёт: нужен бинарь в `PATH` и работающий вход (`jira me`). В проекте
   хранится только `jira: {enabled, project}` в `projects.json` (ADR-0004); ключ проекта - в аргумент `-p`.
3. Аргументы проверяются до вызова: ключ задачи по `^[A-Z][A-Z0-9_]*-\d+$`, ключ проекта по `^[A-Za-z][A-Za-z0-9_]*$`; детали и адрес
   запрашиваются только по ключу из последнего списка проекта, как описание задачи в ADR-0010; адрес для браузера принимается, только если он
   `http` или `https`.
4. Вывод `jira` - чужой текст: цвет и управляющие символы вычищаются, документ ADF приводится к тексту, описание режется до 20 000 знаков;
   интерфейс рисует его через `textContent`. Разбор следует двум видам `--raw` (список - плоский вид `jira-cli`, просмотр - тело REST).
5. Отказ входа (`Unauthorized`, 401/403, «needs a Jira API token») останавливает запросы списка до «Обновить»: опрос по таймеру не должен
   повторять неверные учётные данные. Прочие отказы опрос не останавливают. Нет бинаря, нет настройки, вход не принят, прочее - разные
   причины, каждая с командой, которая её исправляет.
6. Сводка статуса опрашивается из интерфейса: при выборе проекта, при открытии карточки (данные старше минуты), по «Обновить» и раз в 5
   минут, пока окно на виду. Выборки MR автора и рецензента идут по очереди и делят общий пул процессов (ADR-0008, п.4); Jira - параллельно.
7. Старт сессии по задаче Jira - `session:create` с `{jira: {key}}`: главный процесс строит первое сообщение из ключа (чтение задачи,
   план, код не править до подтверждения), название и описание не попадают в него. Намерение MR `ci` («разобрать упавший пайплайн») строится
   так же из проверенной ссылки MR.
8. Проверка: тесты `test/jira.test.ts` (разбор фикстур по формам `jira-cli`, запросы, отказы, защита от повтора неверного входа, ключи,
   настройки проекта, старт сессии), `test/status-model.test.ts` (уровни, внимание, связь с MR) и дымовой тест окна с подставным `jira`;
   прогон на живой Jira не выполнен (D-11).

## Consequences

- Positive: Jira в окне без второго способа входа и без секретов в Cyborg; у разработчиков, настроивших `jira-cli`, ничего настраивать
  не надо; отказ входа не плодит неверных попыток.
- Negative: формат `--raw` у `jira-cli` не версионирован - его смена ломает разбор (ответ «не JSON» либо пустой список); работа зависит от
  бинаря и его входа; опрос раз в 5 минут добавляет вызовы `gh`, `glab`, `jira`.
- Risks: у Cyborg нет проверки на живой Jira (Cloud и Data Center - только по тестам и моду); связь задачи с MR по ключу в названии
  либо ветке не находит MR без ключа; категория «в работе» берётся вторым вызовом - при его сбое задачи падают в «Остальные открытые».

## Alternatives Considered

- **REST Jira напрямую с токеном в Cyborg.** Pros: нет зависимости от бинаря. Cons: секрет в Cyborg (ADR-0007: токены не хранить), второй
  способ входа, свои Cloud и Server версии API. Why rejected: у разработчиков вход уже настроен для `jira-cli`.
- **Jira третьим видом трекера (`TrackerKind`).** Pros: общая панель. Cons: ссылка задачи (хост, путь, номер), ключи, фильтры и детали
  панелей рассчитаны на GitHub и GitLab. Why rejected: перестройка всего контура задач ради вида, который не ложится в него.
- **Автоматический запуск сессии по событию (упал пайплайн, назначена задача).** Pros: быстрее реакция. Cons: агент без слова человека
  правит репозиторий. Why rejected: BRD продукта, BR-001.
- **Сводка только по нажатию, без таймера.** Pros: ни одного лишнего вызова. Cons: индикатор без данных бесполезен. Why rejected: D-06.
