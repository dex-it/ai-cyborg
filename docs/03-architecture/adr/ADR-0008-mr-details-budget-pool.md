# ADR-0008 Пайплайн и апрувы MR - второй фазой выборки: GraphQL на источник GitLab, запросы на PR GitHub в пределах бюджета и пула

## Decision Drivers

- Строка MR несёт статус пайплайна и апрувы (brief п.3), а REST-список MR GitHub и GitLab их не отдаёт.
- Только читающие вызовы через `gh`/`glab`; GraphQL - постоянным читающим запросом (ADR-0007 п.1, п.3).
- На Upcore список виден не позже 2 с, детали - не позже 3 с, список не ждёт деталей (brief perf, «Требования»
  п.2, п.3; SRS фичи 02, NFR-2002).
- Лимит REST GitHub - 5000 запросов в час на пользователя, общий с видом задач и с самим пользователем.
- Заголовок открытой сессии MR должен получать свежий пайплайн при каждом обновлении (SRS фичи 02, FR-2013).

## Context

Вид MR/PR читает список открытых MR одним процессом на источник (ADR-0007 п.2). Пайплайн GitHub - сводка check runs
и commit statuses головного коммита, апрувы - ревью PR; пайплайн GitLab - `head_pipeline` одиночного MR, апрувы -
отдельный ресурс. Репозиторий с тысячами открытых PR дал бы тысячи вызовов на одно обновление.

## Decision

1. Фильтр по участникам применяется главным процессом к полной выборке списка до запроса деталей (инженерный
   вывод: search API GitHub ограничен 30 запросами в минуту и 1000 результатами, а список `pulls` всё равно нужен
   для веток и головного коммита). Проверка: при фильтре детали PR GitHub запрашиваются только у прошедших его PR; MR GitLab получают детали
   всех открытых MR источника одним запросом (п.2), фильтр на запрос деталей GitLab не влияет.
2. Детали PR GitHub - отдельные читающие вызовы на PR: check runs и commit status головного коммита и ревью PR
   (внешний источник: документация REST GitHub). Детали MR GitLab - один процесс `glab api graphql` на источник по
   всем открытым MR проекта, страницами по курсору; на хосте без полей правил апрува - п.9 (внешний источник: brief
   perf, «Замер» - GraphQL хоста отдаёт пайплайн и апрувы всех открытых MR одним запросом). Проверка: тест сервиса
   видит у PR GitHub три вызова, у источника GitLab - вызов списка и один `graphql`.
3. Детали PR GitHub запрашиваются не больше чем у 200 PR - самых свежих по дате обновления после фильтра, по всем
   источникам вместе; MR с открытой сессией получают детали сверх предела, их не больше 200; остальным - «не
   получено» (инженерный вывод из лимита REST GitHub). К MR GitLab предел не применяется: GraphQL отдаёт все открытые
   MR источника без вызова на MR. Проверка: на 205 PR детали ровно у 200 самых свежих и у MR с сессией; у GitLab
   вторая страница курсора даёт детали сверх 200.
4. Одновременно обрабатываются не больше 6 PR GitHub и MR с сессией вне списка, вызовы одного MR идут подряд; пул
   один на все выборки сервиса, и освободившийся слот получает первая задача не отброшенной выборки, а задачи
   отброшенной дорабатывают. Перекрывающиеся выборки без «Обновить» ждут GraphQL источника, уже идущий в полёте;
   «Обновить» запускает свой GraphQL и начатый до неё не прерывает (FR-2009). Без «Обновить» процессов `gh`/`glab`
   одновременно не больше 6 плюс число источников (инженерный вывод); каждое «Обновить» во время деталей добавляет
   по процессу GraphQL на источник GitLab, пока прежний не завершится. Проверка: подставной запуск со счётчиком
   незавершённых вызовов не видит больше 6 плюс число источников при трёх перекрывающихся выборках без «Обновить»;
   две перекрывающиеся выборки GitLab без «Обновить» дают один `graphql`, «Обновить» во время деталей - второй
   (`test/mrs.test.ts`).
5. Отказ вызова деталей задевает только своё поле MR: строка остаётся, поле - «не получено»; отказ списка - отказ
   источника целиком (внешний источник: цель, критерии 4 и 6). Отказ GraphQL целиком либо отсутствие MR в ответе -
   «не получено» у задетых MR, отказ страницы оставляет полученные страницы (внешний источник: цель
   `panel-load-perf`, критерии 8, 9). Проверка: тест отказа деталей, отказа страницы списка и отказа `graphql`.
6. Головной коммит из ответа трекера подставляется в путь вызова, только если он hex SHA (инженерный вывод: данные
   трекера не доверены). Проверка: коммит не hex - вызова нет, пайплайн «не получен».
7. MR с открытой сессией, которого нет в списке (влит, закрыт, не прошёл фильтр), запрашивается одиночным вызовом
   MR плюс пайплайн, без апрувов; таких не больше 200 (внешний источник: цель, критерий 18). Проверка: тест
   отслеживаемых MR.

8. Выборка идёт в две фазы: канал `mrs:list` возвращает список сразу после REST-списков вместе с номером выборки и
   ключами MR, чьи детали ожидаются; детали интерфейс забирает вызовом `mrs:details` по этому номеру. Номер
   одноразовый; главный процесс держит не больше 8 незабранных выборок, вытесненная дорабатывает процессы, её
   результат теряется. Запрос GraphQL стартует вместе со списком (внешний источник: brief perf, «Требования» п.3;
   инженерный вывод - pull вместо события, предел 8). Проверка: список возвращается до завершения деталей; номер
   отдаёт детали один раз; неизвестный номер даёт «деталей нет».
9. Запрос GraphQL идёт сначала с полем числа обязательных апрувов; ответ, все ошибки которого - неизвестное поле
   `approvalsRequired`, запоминает хост на время работы приложения, и запрос повторяется без этого поля; память не
   сбрасывается проверкой входа, «Обновить» и сохранением свойств проекта; прочие отказы повтора не дают (внешний источник:
   brief perf, «Замер» - хост без правил апрува; решение составителя по мандату владельца, D-29 фичи 02). Проверка:
   на подменённом хосте без поля первый запрос деталей - два вызова `graphql`, следующие, в том числе после
   «Обновить», - один.

## Consequences

- Positive: стоимость обновления ограничена сверху и не зависит от числа открытых MR; лимит REST не выбирается
  одним обновлением; у GitLab - процесс на страницу из 100 MR, список виден до деталей.
- Negative: у PR GitHub вне двухсот самых свежих пайплайн и апрувы не видны; последовательные вызовы внутри PR
  удлиняют обновление; два способа получения деталей - по виду трекера; деталям новой выборки GitHub может
  достаться очередь отброшенной.
- Risks: двести MR по три вызова - до 600 запросов GitHub на обновление; частые «Обновить» на большом репозитории
  выбирают лимит REST.

## Alternatives Considered

- **Детали у всех MR без предела.** Pros: полнота строки. Cons: 2000 открытых PR - 6000 вызовов `gh`. Why rejected:
  больше часового лимита REST GitHub, ломает и вид задач.
- **GraphQL одним запросом и у GitHub.** Pros: статус, ревью и checks за один вызов. Cons: запрос другого API,
  замера по хосту GitHub нет. Why rejected: brief perf измерил только GitLab; у GitHub - п.2, п.3.
- **REST-вызовы на MR GitLab (одиночный MR и approvals).** Pros: тот же способ, что у GitHub. Cons: 59 вызовов CLI и
  8,3 с на 27 MR Upcore. Why rejected: предел 3 с (brief perf).
- **`glab api --paginate` для GraphQL.** Pros: страницы без своего цикла. Cons: отказ середины отдаёт неразобранный
  хвост и код выхода на весь вывод. Why rejected: «полученные страницы остаются» (п.5) невыполнимо.
- **Детали событием из главного процесса.** Pros: без второго вызова. Cons: канал push с номером выборки, подписка во
  view, ссылка на окно в сервисе; потеря события молчит. Why rejected: п.8.
- **Запрос всегда без `approvalsRequired`.** Pros: один вызов и на первом запросе. Cons: теряется «N из M» на хостах
  с правилами (brief perf п.5). Why rejected: п.9.
- **Пул на каждую выборку.** Pros: выборки независимы. Cons: перекрытие выборок умножает процессы `gh`. Why
  rejected: п.4.
- **Search API GitHub для фильтра.** Pros: фильтр на сервере. Cons: 30 запросов в минуту, своя пагинация до 1000.
  Why rejected: п.1.
- **Вызовы одного MR параллельно.** Pros: быстрее строка. Cons: пул из 6 MR даёт до 18 процессов `gh`. Why rejected:
  п.4.
- **Вытеснять свежие MR ради MR с сессией.** Pros: предел ровно 200. Cons: свежий MR теряет детали. Why rejected:
  MR с сессией добавляются сверх предела (п.3).
- **Фильтр в интерфейсе.** Pros: смена фильтра без запроса. Cons: детали запрашивались бы у всей выборки, аргумент
  фильтра не проверял бы главный процесс. Why rejected: п.1, ADR-0002 п.5.
