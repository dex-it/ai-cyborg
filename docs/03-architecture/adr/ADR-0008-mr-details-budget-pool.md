# ADR-0008 Пайплайн и апрувы MR - запросом на MR в пределах бюджета и пула процессов

## Decision Drivers

- Строка MR несёт статус пайплайна и апрувы (brief п.3), а список MR GitHub и GitLab их не отдаёт: нужны вызовы
  на каждый MR.
- Только читающие REST-вызовы через `gh`/`glab`, без полей запроса и без GraphQL (ADR-0007 п.1, п.3).
- Лимит REST GitHub - 5000 запросов в час на пользователя, общий с видом задач и с самим пользователем.
- Заголовок открытой сессии MR должен получать свежий пайплайн при каждом обновлении (SRS фичи 02, FR-2013).

## Context

Вид MR/PR читает список открытых MR одним процессом на источник (ADR-0007 п.2). Пайплайн GitHub - сводка check runs
и commit statuses головного коммита, апрувы - ревью PR; пайплайн GitLab - `head_pipeline` одиночного MR, апрувы -
отдельный ресурс. Репозиторий с тысячами открытых PR дал бы тысячи вызовов на одно обновление.

## Decision

1. Фильтр по участникам применяется главным процессом к полной выборке списка до запроса деталей (инженерный
   вывод: search API GitHub ограничен 30 запросами в минуту и 1000 результатами, а список `pulls` всё равно нужен
   для веток и головного коммита). Проверка: при фильтре детали запрашиваются только у прошедших его MR.
2. Детали MR - отдельные читающие вызовы на MR: GitHub - check runs и commit status головного коммита и ревью PR;
   GitLab - одиночный MR (`head_pipeline`) и его approvals (внешний источник: документация REST GitHub и GitLab -
   список MR GitLab `head_pipeline` не несёт). Проверка: тест сервиса видит у MR GitHub три вызова, у MR GitLab два.
3. Детали запрашиваются не больше чем у 200 MR - самых свежих по дате обновления после фильтра, по всем источникам
   вместе; MR с открытой сессией получают детали сверх предела, их не больше 200; остальным - «не получено»
   (инженерный вывод из лимита REST GitHub). Проверка: на 205 MR детали ровно у 200 самых свежих и у MR с сессией.
4. Одновременно обрабатываются не больше 6 MR, вызовы одного MR идут подряд; процессов `gh`/`glab` одновременно не
   больше 6 плюс число источников (инженерный вывод). Проверка: подставной запуск со счётчиком незавершённых
   вызовов не видит больше этого числа.
5. Отказ вызова деталей задевает только своё поле MR: строка остаётся, поле - «не получено»; отказ списка - отказ
   источника целиком (внешний источник: цель, критерии 4 и 6). Проверка: тест отказа деталей и отказа страницы.
6. Головной коммит из ответа трекера подставляется в путь вызова, только если он hex SHA (инженерный вывод: данные
   трекера не доверены). Проверка: коммит не hex - вызова нет, пайплайн «не получен».
7. MR с открытой сессией, которого нет в списке (влит, закрыт, не прошёл фильтр), запрашивается одиночным вызовом
   MR плюс пайплайн, без апрувов; таких не больше 200 (внешний источник: цель, критерий 18). Проверка: тест
   отслеживаемых MR.

## Consequences

- Positive: стоимость обновления ограничена сверху и не зависит от числа открытых MR; лимит REST не выбирается
  одним обновлением.
- Negative: у MR вне двухсот самых свежих пайплайн и апрувы не видны; последовательные вызовы внутри MR удлиняют
  обновление.
- Risks: двести MR по три вызова - до 600 запросов GitHub на обновление; частые «Обновить» на большом репозитории
  выбирают лимит REST.

## Alternatives Considered

- **Детали у всех MR без предела.** Pros: полнота строки. Cons: 2000 открытых PR - 6000 вызовов `gh`. Why rejected:
  больше часового лимита REST GitHub, ломает и вид задач.
- **GraphQL одним запросом.** Pros: статус, ревью и checks за один вызов. Cons: требует полей запроса. Why rejected:
  ADR-0007 п.3.
- **Search API GitHub для фильтра.** Pros: фильтр на сервере. Cons: 30 запросов в минуту, своя пагинация до 1000.
  Why rejected: п.1.
- **Вызовы одного MR параллельно.** Pros: быстрее строка. Cons: пул из 6 MR даёт до 18 процессов `gh`. Why rejected:
  п.4.
- **Вытеснять свежие MR ради MR с сессией.** Pros: предел ровно 200. Cons: свежий MR теряет детали. Why rejected:
  MR с сессией добавляются сверх предела (п.3).
- **Фильтр в интерфейсе.** Pros: смена фильтра без запроса. Cons: детали запрашивались бы у всей выборки, аргумент
  фильтра не проверял бы главный процесс. Why rejected: п.1, ADR-0002 п.5.
