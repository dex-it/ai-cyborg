# BRD фичи 01 - ядро и загрузчик плагинов

Источник: запрос владельца (2026-11-02), [ресёрч](../../research/README.md) и [SAD2](../../03-architecture/design/sad2.md) (проверен [ресёрчем-2](../../research/sad2-validation.md)). Родитель - [BRD продукта](../brd.md): BR-CH-001, BR-CH-005, BR-CH-006, BR-CH-007.

## 1. BRS overview

Чтобы функции могли жить плагинами, нужно ядро, которое открывает воркспейс, находит плагин, проверяет его манифест, версии и граф контрактов до запуска кода, раскладывает плагины по хостам, следит за ними и переживает их сбой. Ядро не знает предметной области (агентов, сессий, файлов, проектов, трекеров): критерий компактности - задача входит в ядро, только если она нужна всем плагинам или окну без плагинов и плагин не решит её сам, не нарушив гарантию остальным. Процессы агентов (pty) живут дольше плагина, поэтому их держит ядро ([ADR-CH-0012](../../03-architecture/adr/ADR-CH-0012-hosts-watchdog-pty-host.md)). Образцы решили это по-разному: dsh - вендорным Cordis с процессом, где даже ядро - плагин; bb - SDK и серверной активацией с откатом и безопасным режимом. Мы делаем собственное минимальное ядро ([ADR-CH-0001](../../03-architecture/adr/ADR-CH-0001-core-and-plugins.md), [ADR-CH-0009](../../03-architecture/adr/ADR-CH-0009-core-boundary-and-compactness.md)).

## 2. Business purpose

Дать устойчивое основание для плагинов: предсказуемый запуск, видимый статус, изоляция сбоев (зависший или упавший плагин не трогает окно, другие хосты и процессы агентов) и понятный набор для автора.

## 3. Business scope

Внутри: воркспейс как главная сессия (процесс на воркспейс, замок); манифест и его схема; версии API и контрактов; обнаружение и граф контрактов до запуска кода; активация (в том числе ленивая); хосты плагинов, группы по `config` и сторож с порогами; pty-хост ядра; безопасный режим; раздел «Плагины Cyborg» и журнал; флаг `--dump-plugins`; набор автора (шаблон, тестовый хост, проверка дисциплины первого этапа). Второй этап (по поводу): процесс на плагин с `--permission`, `Compartment` вторым слоем, установка и подпись.

`non-goals`:

- установка сторонних плагинов, окна согласия и каталог на первом этапе (второй этап, по поводу);
- горячая выгрузка плагинов и каскад перезапуска в v1;
- перенос функций в плагины (фича 03);
- агент, сессии, файлы, проекты и трекеры в ядре.

## 4. Стороны и сценарии

Мейнтейнер, автор плагина, пользователь. Сценарии: [сбой плагина](../../02-use-cases/plugin-failure-isolated/scenario.md), [терминал переживает хост](../../02-use-cases/terminal-survives-host-restart/scenario.md), [автор плагина](../../02-use-cases/author-writes-plugin/scenario.md), [мейнтейнер добавляет функцию](../../02-use-cases/maintainer-adds-feature/scenario.md).

## 5. Меры эффективности

| MOE | Значение |
|---|---|
| Сбой активации или вызова плагина не роняет окно и другие хосты | 100% в тестах отказов |
| Зависший хост перезапущен сторожем в пределах порога (стартовые значения: 15 с без ответа, 3 перезапуска за 5 минут) | 100% в тесте сторожа; значения подтверждаются тестом, прецедента нет |
| Причина отказа загрузки (версия, граф, раздел `config`) видна в интерфейсе и журнале | 100% плагинов |
| Выгрузка плагина оставляет 0 регистраций (HMR-safety тест реестра) | 100% реестров |
| pty с `persist` переживает перезапуск хоста плагина и окна | 100% в тестах с подставной программой |
| Нарушения дисциплины первого этапа (импорт `node:*`, `electron`, чужого плагина; не клонируемые данные) | 0, проверяется тестами |
| Имён плагинов и предметных сущностей в коде ядра | 0 |
| Добавление нового плагина-пилота (`session-notifications`) не правит общих файлов | 0 общих файлов |
