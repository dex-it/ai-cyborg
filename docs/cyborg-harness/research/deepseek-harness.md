# Разбор DeepSeek Harness (dsh)

Источник: репозиторий [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness), коммит `ce7073d5` (2026-10-30), страница [deepseek.com/en/harness](https://www.deepseek.com/en/harness/), документация [deepseek-harness.github.io](https://deepseek-harness.github.io/deepseek-harness/). Код только читался: ничего не устанавливалось и не запускалось. Метка **Факт** - прочитано в коде или документе (путь от корня репозитория dsh), **Вывод** - наша интерпретация. Документы в репозитории продублированы на английском и китайском, читались английские. Статью про «пространственно-временную компонуемость», на которую ссылается README, мы не читали.

## 1. Что это

Открытый харнес для агентов от DeepSeek, лицензия MIT. Статус - «developer preview», в README: «THERE WILL BE COMPATIBILITY-BREAKING CHANGES». Девиз - **everything is a plugin**: на странице продукта плагины расширяют инструменты, навыки (skills) и интерфейс, ставятся из менеджера плагинов или создаются в чате («Creator mode»). Официальные плагины: Agent teams, Auto approval review, Scheduled tasks, Voice input, Terminal, Agent loop, Subagents (часть помечена экспериментальной). Сообщество помечает свои плагины темой GitHub `dsh-plugin` (кода, который эту тему читает, мы не нашли). Запуск: `npx @deepseek-ai/dsh web` (Web UI на 127.0.0.1:3080) или настольное приложение (macOS Apple silicon, Windows). Поддержка внешних агентов на странице продукта не заявлена.

Размер: 372 пакета в `packages/*/*` (группы: client 69, experimental 65, session 22, util 21, core 10, shell 10, api 10), около 525 тыс. строк исходников и 711 тыс. строк тестов, 359 файлов в `scripts/`, около 2650 заметок для агентов.

## 2. Основа: Cordis

**Факт.** Весь фреймворк - вендорный форк [Cordis](https://github.com/cordiverse/cordis) (`vendor/cordis/src`, 2811 строк, плюс загрузчик на 1143; журнал локальных правок в `vendor/README.md`: 22 действующие записи, нумерация дошла до V25, следующая V26).

| Понятие | Что это |
|---|---|
| Плагин | Функция, объект с `apply(ctx, config)` или класс-наследник `Service`. Лоадер дополнительно требует форму экспорта: функция экспортирует именованные `name`, `inject`, `Config`, `apply` и **не имеет `default`**; сервис экспортирует `default`-класс |
| Context (`ctx`) | Прокси-хранилище сервисов; `ctx.extend()`, `ctx.isolate(name)`, `ctx.intercept(name, cfg)` создают дочерние контексты и не меняют родителя |
| Сервис | Занимает ключ `ctx.<имя>` (`super(ctx, 'shell')`) |
| `inject` | Список обязательных сервисов. Пока их нет, плагин в состоянии PENDING; исчез или заменён провайдер - зависимые выгружаются и после возвращения сервиса загружаются заново |
| Fiber | Загруженный экземпляр плагина: PENDING, LOADING, ACTIVE, FAILED, UNLOADING, DISPOSED |
| Эффекты | Всё, что плагин зарегистрировал (`ctx.on`, `ctx.plugin`, `ctx.effect`, `ctx.tools.register`), откатывается при выгрузке |
| События | Тип объявляется слиянием деклараций TypeScript; у каждого события режим диспетча: `emit`, `parallel`, `serial`, `bail`, `waterfall`. Waterfall - обёртка вокруг следующего слушателя через `next()`; слушатель, не вызвавший `next()`, обрывает цепочку |
| Горячая замена | Строки `cordis.yml` сопоставляются по `id`, перезагружаются только изменённые; поля конфигурации схемы с `.volatile()` обновляются вживую, остальные перезапускают плагин |

Три коротких примера из документации:
1. **Эффект с откатом.** `ctx.effect(() => { const t = setInterval(...); return () => clearInterval(t) })`: деструктор вызывается при выгрузке.
2. **Три роли.** `ShellExecutor extends Service` объявляет `ctx.shell`; провайдер `bash-local` его реализует; потребитель `tool-bash` имеет `inject = ['tools','shell','systemPrompt',...]`. Подмена `bash-local` на `bash-sandbox` в конфиге не затрагивает схему инструмента для модели.
3. **Перехват с waterfall.** `ctx.on('tools/pre-execute', async (exec, next) => deny ? {kind:'deny'} : next())` - политика прав в виде слушателя.

## 3. Что в ядре, что плагины

**Факт.** «Привилегированного ядра нет» (`docs/architecture.md`). Минимум, который плагином не является: вендорный Cordis и лаунчер (`apps/cli`, `packages/boot/app-boot`). Даже сессионный журнал, реестр инструментов и цикл агента - плагины (цикл можно заменить целиком). В `docs/capability-seams.md` классифицированы 108 сервисов `ctx`: 61 `core`, 36 `seam`, 10 `service`, 1 `bundle`; «ядро» тут означает неподменяемый сервис, а не минимум. Группа `core/` занимает около 14,6 тыс. из 525 тыс. строк.

Фактический «центр» по входящим связям: `session` (106 пакетов зависят), `llm` (98), `agent` (82), `tools` (65), `system-prompt` (38).

## 4. Точки расширения (seams)

**Факт.** Seam - три роли: **Definition** (абстрактный класс или реестр, не TypeScript-`interface`), **Provider**, **Consumer** (`docs/capability-seams.md`). Роли разносят по пакетам, только когда они реально развиваются независимо: правило «не дели заранее», пока нет второго провайдера - один пакет. Кроме сервисных seam есть реестры провайдеров (`ctx.llm.registerAdapter`, `ctx.tools.register`), события-перехваты (`agent/pre-step`, `tools/pre-execute`, `tools/execute`, `tools/post-execute`), `ctx.tools.guard()` - монотонный запрет после политик, регистрации в области одного агента, декларативные наборы плагинов на сессию и слоты интерфейса.

Контракт seam держится на типах TypeScript, JSDoc, ревью и тестах пакета; рантайм-схемы контракта нет. Общий набор тестов на соответствие провайдера нашёлся только для хранилища (`runKvBackendContract`).

## 5. Манифест, распространение, совместимость

**Факт.** Манифест - блок `dsh` в `package.json`: `bundle.patch` (YAML-патчи конфигурации), `profile.bundles`, `client` (браузерная половина), `engines.dsh` (диапазон версий; без него проверяются `peerDependencies` на пакеты dsh), `locale/en.json` с названием и иконкой. **Бандл** - npm-пакет со слоем конфигурации, **профиль** - каталог `$DSH_HOME/profiles/<имя>`. Слои применяются по порядку: бандлы, профиль, домашний патч, `--patch`; патч по `id` заменяет конфигурацию строки целиком без глубокого слияния. Итоговое дерево показывает `dsh --profile web --dump-config`.

Установка: `dsh plugin add` через pnpm внутри профиля (npm, `github:`, tarball, локальная ссылка); установка из git выполняет `prepare` и требует явного разрешения исполнять код. Маркет - файл `index.json` формата 1 из экспериментального бандла «Custom plugin indexes» («DSH ships no index source»); генератор `apps/plugin-market-generator` только скачивает, ничего не исполняет.

Совместимость: до импорта плагина лаунчер сверяет `engines.dsh` с версией рантайма, несовместимый не импортируется («это не песочница»); исключение выдаётся по точной паре `пакет@версия` + версия рантайма с `acceptRisk: true`. Политика ломающих изменений: API «pre-stable», каждое внешне видимое ломание сразу фиксируется в `docs/upgrade-guide/v<версия>/<пункт>/guide.md` (формат - ровно `Change` и `Migration`, до 500 слов; сейчас 91 гайд в 11 версиях). Форматы данных версионируются отдельно: формат сессии мигрирует цепочкой `vN` в `vN+1`, индекс маркета - `format: 1`, манифест - `manifestVersion: 1`.

## 6. Границы модулей

**Факт.** Иерархия строго `packages/<группа>/<пакет>`; официальный рантайм не может зависеть от группы `experimental` (проверка в `scripts/check-workspace-constraints.ts`); `verify-package-dependencies` восстанавливает зависимости по импортам, `verify-runtime-closure` и `verify-client-domain-graph` проверяют замкнутость. Документ `docs/defensive-patterns/` - набор «жёстких» правил с указанием, чем проверяется, но часть применяется «в ревью», а не автоматикой. Автоматической проверки правила «расширения зависят от Definition, а не от конкретных провайдеров» не нашли; правил импортных границ между плагинами в линтере тоже.

## 7. Интерфейс и конфигурация

**Факт.** Конфигурация плагина - экспортированная схема Schemastery `Config`; каталог всех настроек (5054 строки) генерируется из исходников. `ctx.settings` строит формы из volatile-полей активных строк, `config-editor` записывает правки патчем профиля, при правке формы действует оптимистичная ревизия. Плагин с интерфейсом - пакет из двух половин: Host и Client, браузерная половина тоже приложение Cordis. Вклад в интерфейс: `ctx.slots.register({name,id,order}, Component)`; слоты типизированы слиянием деклараций и имеют cardinality (`single`, `list`, `keyed`, `chain`) и область; **компонент никогда не получает `ctx`**. Связь Host и Client - методы `@Remote` (Typert: декораторы и генерация клиента из типов), транспорт `POST /api/<ns>/<method>`.

Desktop - Electron вокруг полного Web-приложения: дочерний процесс запускает тот же профильный раннер, окно сразу грузит упакованный Web, ждёт boot-инъекции и стартует клиент в том же документе. Хост слушает порт, выданный ОС, на 127.0.0.1. Версия Electron и версия dsh всегда совпадают. Отдельный профиль `desktop`, принадлежащий приложению; плагины ставятся тем же менеджером через встроенный pnpm.

## 8. Харнес для агентов

**Факт.**
- **Цикл.** Ход (turn) = ноль или больше шагов (step); шаг = один запрос к модели плюс вызванные инструменты. Порядок: `turn/start`, сборка system prompt и схем инструментов, `agent/pre-step`, `step/start`, `agent/request`, запись в лог, поток `llm/stream`, `assistant/message`, инструменты, `step/end`, `turn/end`. Правило: **«модель видела = залогировано»**.
- **Конвейер инструмента.** `tool/call` пишется до выполнения; затем `tools/pre-execute` (ловушки, права, песочница) с решениями `allow | deny | cancel | ask`, монотонные guards (**могут только запрещать**), `tools/execute` (таймаут, ретраи), тело, `tools/post-execute`, `tool/result`. `ask` идёт в канал подтверждения; нет канала или ответа - вызов отклоняется. Исход подтверждения закрыт: `allowed-once | rejected | cancelled | unavailable`, разрешает только первый. Политика на сессию `ask` или `never` (режим для CI).
- **Песочница.** Режимы `read-only`, `workspace-write`, `danger-full-access` (только запись в файлы; сеть не ограничивается). Бэкенды: Linux bwrap и Landlock, macOS Seatbelt, Windows ACL. Каждый запуск сообщает `full` или `partial`; нет подходящего runner - `SANDBOX_UNAVAILABLE`, молча без изоляции команда не запустится. На Windows `bash-sandbox` отключён. Умолчание: `workspace-write` плюс `ask`.
- **Внешние агенты.** В dsh внешний агент - субагент: `subagent-claude-code` запускает настоящий Claude Code через Agent SDK (один свежий `query()` и один процесс на задачу, непривилегированный режим, `AskUserQuestion` отключён, окружение очищено от учётных данных родителя, родитель получает только итоговый ответ), `subagent-codex` (app-server протокол), `subagent-acp` (любой ACP-агент), `subagent-dsh-sdk` (другой dsh). Контракт провайдера: `name`, `capabilities`, `inheritsParentContext`, метод `start(request) -> SubagentRun`. **Интерактивный Claude Code в pty с человеком в dsh не встраивается.**
- **Хранение.** Сессия - append-only JSONL-журнал (сжатие Zstandard, единственный писатель, `flush` - единственная гарантия сохранности, оборванный хвост читателю не отдаётся). Версия формата хранится отдельно от версии приложения (`SESSION_FORMAT_VERSION = 4`). Миграции «рядом»: версии, попавшие в релиз, неизменяемы, миграция пишет новый файл `session.vN.jsonl[.zstd]`, исходный не трогает; откат и downgrade не поддерживаются; неподдерживаемая будущая версия даёт явную ошибку. Каждое структурное изменение схемы требует акта в `docs/persistence-changes/` (четыре файла). Урок: миграция сессии в 116 МБ исчерпала 16 ГБ памяти, потому что материализовала всё целиком; её переделали на потоковую.
- **Поверхности.** Профили запуска `dsh --profile <имя>`: `web`, `headless`, `sdk`, `acp`. Доступ к API gateway - генерируемый типизированный клиент `ctx.remote.<namespace>.<method>`; для чужого пира каждый вызов сначала проходит `remoteAccess.decide()`.

## 9. Безопасность

**Факт.** `SAFETY.md` короткий (27 строк): экспериментальное ПО без аудита, песочница и подтверждения не гарантируют изоляцию, рекомендации (минимальные права, одноразовая VM, бэкапы, ревью плагинов). Модели угроз, списка запретов и границ плагинов нет. **Сторонний плагин исполняется в процессе без песочницы** («installed Host code executes in-process outside the workspace sandbox»); действия `plugin_manager` требуют `danger-full-access` или подтверждения на каждый вызов. Подписей и проверки происхождения плагинов не нашли. Web слушает только loopback, нестандартные authority требуют `--trusted-host`, запуск по токену и подписанному cookie. Секреты - отдельный сервис `dsh-credentials`, конфигурация ссылается на ключи по имени. Серверы MCP не включены по умолчанию.

## 10. Сборка, релиз, тесты

**Факт.** pnpm 11, Node 24.9 и выше, tsc с двумя изолированными агрегатами (Host и Client: обе стороны расширяют `Context` одинаковыми ключами) и tsdown. Релиз: сборка tarball'ов на каждый PR, публикация вручную по тегу; единая версия всех пакетов. Обновление Desktop: проверка раз в 10 минут ±20%, принудительная политика, откат с задержкой, установка отклоняется, если Host не подтвердил завершение.

Тесты: unit с 100% покрытием строк по файлам; обязательный **HMR-safety тест** для каждого реестра (выгрузить fiber и проверить очистку); для продуктового плагина - **реальный** композиционный тест через настоящий загрузчик (урок постмортема 0001: ACP падал на подключении из-за лишнего `export default`, хотя были 178 зелёных юнит-тестов); **снапшоты записанных сессий** (167 сценариев для session, плюс sdk, web, acp); браузерные снапшоты в Chromium и WebKit; бенчмарки производительности с бюджетами времени, памяти и масштабирования как обязательный гейт PR. Документы - в трёх файлах с хешами по разделам (en, zh, i18n), проверка парности в CI.

## 11. Слабые места и цена подхода

**Факт.**
- Масштаб и ритуалы: 372 пакета, у каждого README, tsconfig, locale; каждое структурное изменение формата - четыре файла и вдвое больше при двуязычии.
- **Молчаливый PENDING**: плагин с недостающим сервисом ничего не печатает.
- Тонкие места загрузчика: лишний `default`-экспорт теряет `inject`; литерал `!!js` вне `config` и `disabled` работает как «всегда истинно»; необязательный сервис нужно брать через `ctx.get`.
- Waterfall-слушатель, забывший `next()`, тихо глотает поведение по умолчанию; асинхронные деструкторы идут параллельно.
- Разрешение модулей опирается на внутренности Node (Desktop запускает Electron с `--expose-internals`).
- Нет песочницы для плагинов; API pre-stable; ведение форка Cordis (22 действующие локальные правки).
- Контракты seam без общих наборов тестов провайдеров (кроме хранилища).

## 12. Что стоит перенять

1. **Минимальное ядро** как загрузчик плагинов, реестр сервисов, жизненный цикл и событийная шина; всё остальное - плагины поверх.
2. Модель «сервис + `inject` + эффект с откатом»: каждая регистрация возвращает деструктор, плагин выгружается целиком, зависимые перезапускаются каскадом.
3. Три роли Definition, Provider, Consumer для заменяемых возможностей и правило «не дели заранее».
4. **Режимы событий как часть контракта**: наблюдать, перехватывать (waterfall) и монотонно запрещать (`guard`); тип и режим каждого события объявляются в одном месте.
5. Слои конфигурации с адресацией по `id` и команда «покажи итоговую композицию».
6. Конфигурация как схема: изменяемые вживую поля порождают форму настроек.
7. Слоты интерфейса, где компонент не получает контекст.
8. Обязательные тесты: выгрузка реестра и загрузка реальной конфигурации через загрузчик; снапшоты записанных сессий.
9. Манифест с диапазоном совместимости и проверкой до импорта кода.
10. Автоматические проверки границ (запрет импорта плагина из плагина, запрет зависимости от конкретного провайдера).
11. Журнал ломающих изменений (`upgrade-guide`) в момент изменения.
12. Постмортемы как жанр: находка о загрузчике становится тестом или проверкой.
13. Из харнеса: закрытые исходы подтверждения и отказ по умолчанию; guards, которые только запрещают; различие `full` и `partial` в песочнице; версия формата отдельно от версии приложения; миграции «рядом»; события плагинов с флагом `ignorable` и префиксом `plugin:`; тонкая оболочка Electron с экраном восстановления.

## 13. Чего не брать

- Дробление на сотни пакетов: для нас хватит папок-модулей в одном workspace.
- Форк и вендоринг фреймворка: проще написать маленькое собственное ядро.
- Молчаливое ожидание зависимостей: нужен видимый статус «ожидает сервис X».
- Много слоёв конфигурации (бандл, профиль, домашний патч, `--patch`): для приложения с одним пользователем достаточно двух.
- Установку плагинов через pnpm и git с исполнением `prepare`.
- Зависимость от внутренностей Node (`--expose-internals`).
- Двуязычную парность документов, 100% покрытие на файл, 359 скриптов-гейтов.
- Декораторы `@Remote`, Typert и двойную сборку Host и Client: нам хватит типизированного IPC.
- Модель «журнал - источник правды, агент крутится в вашем процессе»: у нас агент живёт в pty и порядок событий не наш.
- Вызов Claude Code через SDK как основной путь: это одноразовый неинтерактивный режим, он противоречит живым параллельным сессиям.
- Идею «сторонний плагин - доверенный код без песочницы» без собственного явного уровня доверия.

## 14. Чего не нашли

Формальной модели угроз, подписей и проверки происхождения плагинов, интерактивного встраивания внешнего агента в pty, общих тестов соответствия провайдеров (кроме хранилища), автоматической проверки «не зависеть от конкретного провайдера», кода, читающего тему `dsh-plugin`, назначения `docs/dependency-catalog.json` (снимок зависимостей устаревшей версии).
