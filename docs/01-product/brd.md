# BRD продукта Cyborg

> Реконструировано из кода и конфигурации, не согласовано: описания продукта от постановщика нет. Где
> предполагаемое поведение совпадает с замыслом, а где оно является дефектом, размечает владелец продукта.

## 1. BRS overview

Документ фиксирует назначение Cyborg, его стороны и границу. Проблема: разработчик, который ведёт несколько
сессий Claude Code сразу, держит их в разрозненных терминалах и отдельно открывает файлы и git-изменения,
которых коснулась сессия. Решение: настольное рабочее место, где каждая нативная сессия Claude Code идёт со своим
деревом файлов, git-статусом и просмотром файлов (`package.json:5`). Ожидаемая выгода: состояние каждой сессии
видно в одном окне без переключения между инструментами. Документ адресован владельцу продукта и составителям
требований и архитектуры.

## 2. Business purpose

Дать разработчику одно место, где видно, что каждая из его параллельных сессий Claude Code делает с
репозиториями проекта, при этом сама сессия остаётся нативной: Cyborg не подменяет Claude Code и не меняет то,
как тот пишет свою историю (`src/main/sessions.ts:22`, `src/main/sessions.ts:26`).

## 3. Business scope

Внутри границы:

- проекты как именованные наборы локальных репозиториев с описанием;
- запуск, ввод, изменение размера и завершение интерактивных сессий Claude Code в выбранном репозитории проекта,
  остальные репозитории проекта подключаются к сессии как дополнительные каталоги;
- дерево файлов сессии с ветками и git-статусом каждого репозитория, следующее за рабочим каталогом сессии;
- просмотр текстовых файлов с подсветкой синтаксиса, только на чтение;
- светлая и тёмная тема по системной настройке.

`non-goals` (выведены из отсутствия в коде, подтверждаются владельцем):

- правка файлов в Cyborg: просмотрщик только читает;
- git-операции, меняющие репозиторий: коммит, переключение ветки, сравнение версий;
- собственный клиент модели или обёртка над API: работа идёт только через CLI `claude`;
- удалённые машины и многопользовательская работа: все пути и процессы локальные;
- восстановление сессий после перезапуска Cyborg.

## 4. Business overview

Сегодня разработчик запускает `claude` в эмуляторе терминала, по окну на сессию, а файлы и изменения смотрит в
редакторе или через git отдельно. Связь «какая сессия что меняет» держится в голове. Нет данных о том, как
постановщик видит процесс сейчас - открытый вопрос 1.

## 6. Business environment

Внешние силы: Claude Code CLI и его механизм хуков, на который Cyborg опирается целиком, - смена формата событий
или флагов CLI ломает продукт без изменения в нём; git как источник статуса; Electron и нативный модуль
терминала, привязанные к версии рантайма. Регулятора и юрисдикции у предмета не выявлено.

## 7. Mission, goals and objectives

### BR-001 Параллельные нативные сессии в одном окне

- **Требование:** разработчик ведёт несколько сессий Claude Code одновременно в одном окне, каждую в контексте
  выбранного проекта и его репозитория.
- **traced from:** Business purpose; сторона «разработчик».
- **rationale:**
  - reason: цель продукта - собрать параллельные сессии в одном месте (`package.json:5`);
  - assumptions: сессия - нативный процесс `claude`, а не встроенный клиент;
  - relationships: сценарий 1 раздела 17;
  - design constraints: нативность сессии задана - транскрипт и поведение Claude Code не должны отличаться от
    запуска в терминале (`src/main/sessions.ts:26`).
- **MOE:** разработчик переключается между своими сессиями и видит вывод каждой, не открывая другой терминал
  (качественная).

### BR-002 Видимость изменений сессии

- **Требование:** для каждой сессии разработчик видит файлы её рабочего каталога и других репозиториев проекта с
  текущей веткой и git-статусом, обновляющимися по ходу работы сессии.
- **traced from:** Business purpose; сторона «разработчик».
- **rationale:**
  - reason: связь «сессия - что она меняет» сейчас держится в голове (раздел 4);
  - assumptions: изменения сессии отражаются в git-статусе рабочих деревьев;
  - relationships: сценарий 2 раздела 17;
  - design constraints: нет.
- **MOE:** после действия сессии над файлами разработчик видит изменённый файл отмеченным в дереве этой сессии
  без ручного обновления (качественная).

### BR-003 Просмотр файла на месте

- **Требование:** разработчик открывает файл из дерева сессии и читает его с подсветкой синтаксиса, не покидая
  рабочего места.
- **traced from:** BR-002.
- **rationale:**
  - reason: увидев изменённый файл, разработчик хочет прочитать его там же;
  - assumptions: правку файла ведёт сессия или внешний редактор, Cyborg только показывает;
  - relationships: сценарий 2 раздела 17;
  - design constraints: только чтение - граница non-goals раздела 3.
- **MOE:** файл, открытый из дерева, показывает актуальное содержимое с диска при каждом показе (качественная).

## 10. Business processes

«Как есть» - раздел 4. «Как будет»: разработчик заводит проект из репозиториев, запускает сессию в одном из них,
следит за деревом и вкладками файлов этой сессии, переключается между сессиями полосой вкладок.

## 11. Business operational policies and rules

- Сессия Claude Code не оборачивается: Cyborg добавляет к ней только свои хуки.
- Каждая сессия - изолированное рабочее пространство: дерево, раскрытые каталоги и вкладки файлов не делятся с
  другими сессиями (`src/renderer/app.ts:16`).

## 12. Business operational constraints

- Работа требует установленного CLI `claude`, доступного из логин-оболочки пользователя, и `git`.
- Файл больше 5 МБ и двоичный файл не показываются (`src/main/files.ts:9`).

## 16. High-level operational concept

Cyborg для разработчика - пульт поверх его собственных сессий Claude Code: сессии работают как в терминале, а
Cyborg добавляет контекст - проект, дерево, статус, просмотр.

## 17. High-level operational scenarios

1. Разработчик выбирает проект и запускает сессию в репозитории; при нескольких репозиториях выбирает один, прочие
   подключаются к сессии дополнительными каталогами. Альтернатива: у проекта нет репозиториев - запуск недоступен.
2. Сессия меняет файлы; дерево сессии отмечает изменения, разработчик открывает файл и читает его. Альтернатива:
   сессия сменила рабочий каталог - дерево переходит к новому корню.
3. Разработчик закрывает сессию либо окно; процессы сессий завершаются.
