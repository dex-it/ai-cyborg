# SRS фичи 02 - вид MR/PR в панели задач

## 1. SRS overview

Требования системы к вкладке «MR/PR» панели задач: выборка открытых MR GitLab и PR GitHub, строка MR, фильтр и
сортировка, действия «Ревью» и «Доработать» со стартом сессии Claude Code, заголовок сессии MR. Вход - BRD фичи
(`brd-feat.md`, BR-2001, BR-2002), цель трека `mr-view` и её критерии «готово» 1-24. Основания решений и допущений -
`decision-log.md` (D-NN); ссылки на D-NN фичи 01 помечены «фичи 01».

## 2. Purpose

Задать наблюдаемое поведение вида MR/PR и старта сессии по MR так, чтобы правка проверялась по требованию, а не по
коду.

## 3. Scope

Специфицируется часть Cyborg: чтение MR, пайплайнов и апрувов через `gh`/`glab`, их показ, старт сессии из MR.
Вне продукта: трекеры и их CLI, их вход; запись в трекер; checkout ветки MR (делает агент сессии). Общее с панелью
задач - кнопка «Задачи» и вкладочная шапка панели (FR-1001), источники и их настройки (FR-1002, FR-1009, FR-1010),
только чтение трекера и git (FR-1016), проверка `session:create` (FR-1017) - специфицировано в SRS фичи 01 и здесь
не повторяется.

## 4. Product perspective

Главный процесс запускает `gh` и `glab` без оболочки, интерфейс получает список каналом `mrs:list`, а пайплайн и
апрувы - вторым вызовом `mrs:details` по номеру выборки, через preload-API (ADR-0002, ADR-0008 п.8). Доступ к трекерам - ADR-0007, детали MR - ADR-0008.

## 5. Product functions

Список открытых MR проекта с фильтром и сортировкой; пайплайн и апрувы MR; «Ревью», «Доработать» и «К сессии» у MR;
заголовок сессии MR со статусом и пайплайном; обновление по открытию вкладки и кнопке.

## 6. User characteristics

`inherited`: BRD продукта, раздел 5 (разработчик, ведущий сессии Claude Code).

## 7. Limitations

- Новых npm-зависимостей нет; API трекеров - через установленные `gh`/`glab` (цель, граница).
- Проект в файле воркспейса несёт поле `trackers` из двух флагов (ADR-0014 п.6), MR своих полей не добавляет.
- Git - только читающие команды (ADR-0005 п.3); GraphQL - только читающий запрос деталей MR GitLab (FR-1016, D-28).

## 8. Assumptions and dependencies

- `gh` 2.74 и `glab` 1.36, как у фичи 01 (D-20 фичи 01).
- Действие «Ревью» опирается на установленную у пользователя команду `/dex-auto:auto`.
- Допущения цели D-01..D-08 открыты до подтверждения владельцем.

## 9. Apportioning of requirements

Главный процесс: FR-2001, FR-2002, FR-2003, FR-2004, FR-2005, FR-2011, FR-2016, NFR-2001, NFR-2002.
Интерфейс: FR-2006, FR-2007, FR-2008, FR-2009, FR-2010, FR-2012, FR-2013, FR-2014, FR-2015.

## 11. External interfaces

### FR-2001 Источники MR - источники задач

- **Требование:** источник MR - тот же, что источник задач (FR-1002): fetch-remote репозиториев текущего проекта,

  (FR-1010), отдельной галочки и поля для MR нет; выключенный источник не опрашивается. MR, пришедший

  регистре и номер. MR других проектов в списке нет.
- **traced from:** BR-2001.
- **источник:** цель, критерии 2 и 3; brief п.1, п.2; D-23.
- **rationale:** reason - «только из remote репозиториев текущего проекта», «источники общие» (brief); assumptions
  - нет; relationships - сценарий 5 BRD продукта; design constraints - NFR-1002.
- **verification:** испытание - `test/mrs.test.ts` («только remote своего проекта; MR через два репозитория - одна
  строка», «выключенный источник не опрашивается»).
- **класс:** External interfaces. **origin:** source.

- **traced from:** BR-2001.
- **источник:** цель, критерий 4; brief п.1 («открытые MR»); D-09.
- **rationale:** reason - «открытые MR» не ограничены числом; assumptions - «все страницы» по конвенции FR-1003;

### FR-2003 Пайплайн и апрувы MR

- **Требование:** у MR определяются статус пайплайна и апрувы (D-04):
  - GitHub, пайплайн - сводка check runs и commit statuses головного коммита: ни одного check run и ноль statuses -
    «нет пайплайна» (D-16); хотя бы один упавший (conclusion `failure`, `timed_out`, `action_required` либо
    сводка `failure`/`error`) - «упал»; иначе идущий - «идёт»; иначе ожидающий - «ожидает»; иначе отменённый -
    «отменён»; иначе «успешен»;
  - GitLab - один запрос `glab api graphql` на источник по всем открытым MR проекта, страницами по 100 по курсору
    `pageInfo{hasNextPage endCursor}`; обход останавливается на пустом либо повторном курсоре (D-28). Пайплайн -
    `headPipeline.status` в нижнем регистре: `null` - «нет пайплайна»; `success`, `failed`, `running`, `pending`,
    `canceled` - «успешен», «упал», «идёт», «ожидает», «отменён»; прочее - статусом трекера в нижнем регистре
    (D-17), те же слова, что давал REST. MR сопоставляется со строкой списка по `iid`, приведённому к числу;
  - апрувы - «апрувов: N»; у GitLab N - число `approvedBy`, при заданном числе обязательных (`approvalsRequired`) -
    «апрувов: N из M»; хост, ответивший на запрос с `approvalsRequired` только ошибками неизвестного поля,
    запоминается на время работы приложения (проверка входа, «Обновить» и сохранение свойств проекта его не сбрасывают), и
    запрос повторяется без этого поля - «апрувов: N» (D-29); у GitHub N - число пользователей, чьё последнее ревью
    среди APPROVED, CHANGES_REQUESTED, DISMISSED - APPROVED (D-15).
  Головной коммит, не являющийся hex SHA, даёт пайплайн «не получен» без вызова CLI (D-19).
- **traced from:** BR-2001.
- **источник:** цель, критерий 5; brief п.3 («статус пайплайна, апрувы»); D-04, D-15..D-17, D-19; цель
  `panel-load-perf`, критерии 6, 8, 10, 11; brief perf, «Замер» (запрос GraphQL, хост без полей правил апрува), п.5;
  D-28, D-29.
- **rationale:** reason - бриф п.3; два REST-вызова на MR GitLab давали 8,3 с на 27 MR (brief perf, «Замер»);
  assumptions - D-04, D-29; relationships - сценарий 5; design constraints - только читающие запросы (FR-1016,
  ADR-0007 п.3, ADR-0008).
- **verification:** испытание - `test/mrs.test.ts` («githubPipeline: приоритеты», «без check runs и статусов -
  «нет пайплайна»», `gitlabPipeline`, `approvalsText`, `githubApprovals`, «головной коммит не hex», «GitLab: список
  и один graphql на источник», «пайплайн GraphQL теми же словами, что REST», «страницы по курсору», «хост без полей
  правил: первый запрос повторяется без них, хост запоминается»).
- **класс:** External interfaces. **origin:** source; сопоставление по `iid` числом и признак неизвестного поля -
  derived.

### FR-2004 Отказ источника и не полученные поля

- **Требование:** отказ выборки списка источника показывается строкой «<источник>: <причина>» с причинами FR-1007,
  MR остальных источников видны. Не получены пайплайн либо апрувы одного MR - строка остаётся в списке, в этом поле
  «—», отказ другого поля его не задевает. У GitLab: MR списка, которого нет в ответе GraphQL (закрыт между вызовами,
  `project: null`), - «—» в пайплайне и апрувах без отказа источника; отказ запроса GraphQL целиком (код выхода,
  HTTP ≥ 400, ответ без `data`, не JSON) - «—» у MR источника, строки остаются; отказ страницы - детали полученных
  страниц остаются, у прочих MR «—». Ответ с `errors` при наличии `data` отказом не считается.
- **traced from:** BR-2001.
- **источник:** цель, критерий 6; D-26; цель `panel-load-perf`, критерии 8, 9.
- **rationale:** reason - деградация показывает причину (BRD продукта, раздел 13); assumptions - конвенция
  FR-1007; отсутствующий в ответе MR - отказ поля, а не источника; relationships - сценарий 5, альтернатива;
  design constraints - ADR-0008 п.5.
- **verification:** испытание - `test/mrs.test.ts` («отказ одного источника не прячет MR другого», «отказ деталей
  одного MR даёт «—» только в своём поле», «отказ второй страницы: детали первой остаются», «отказ graphql целиком:
  «—» в деталях, строки остаются, повтора нет», «отказ списка GitHub не мешает деталям GitLab»).
- **класс:** External interfaces. **origin:** source; частичный ответ с `errors` и `data` - derived.

### FR-2005 Фильтр MR

- **Требование:** фильтр - одно из «Все» (по умолчанию), «Назначено мне», «Я ревьюер» (D-05). «Назначено мне» -
  MR, где пользователь хоста среди assignees; «Я ревьюер» - GitLab: пользователь среди reviewers, GitHub: ревью
  запрошено у пользователя лично (`requested_reviewers`). Пользователь - логин `gh api user` (GitHub) и пользователь
  хоста из `glab auth status` (GitLab), сравнение без учёта регистра. Фильтр применяет главный процесс по полной
  выборке (D-10). Пользователь не получен: при «Назначено мне» и «Я ревьюер» - отказ источника, выборка без фильтра
  не подменяет отфильтрованную; при «Все» - список, у всех MR действие «Ревью» (D-18).
- **traced from:** BR-2001.
- **источник:** цель, критерий 7; brief п.4 («Фильтр: «назначено мне», «я ревьюер»»); D-05, D-10, D-18.
- **rationale:** reason - бриф п.4; assumptions - D-05; relationships - сценарий 5; design constraints - FR-1004
  (без логина фильтр не применяется вслепую).
- **verification:** испытание - `test/mrs.test.ts` (`filterMrs`, «фильтры: «Назначено мне» и «Я ревьюер» по
  логину gh», «логин не получен: с фильтром - ошибка источника, без фильтра - список»).
- **класс:** External interfaces. **origin:** source; поведение «Все» без логина - derived.

### FR-2016 Проверка аргументов каналов MR

- **Требование:** главный процесс отклоняет ошибкой: `mrs:list` с проектом не строкой, фильтром вне трёх значений,
  отслеживаемыми MR не массивом либо больше 200, ссылкой на MR, не проходящей правила ссылки FR-1017, признаком

  MR) отбрасываются.
- **traced from:** BR-2002; ADR-0002 п.5.
- **источник:** цель, критерий 22; D-22; цель `panel-load-perf`, граница «На усмотрение реализации» (аргументы нового
  канала проверяет главный процесс).
- **rationale:** reason - интерфейс показывает недоверенные данные (ADR-0002); assumptions - нет; relationships -
  нет; design constraints - FR-1017.
- **verification:** испытание - `test/mrs.test.ts` (`validateMrListArgs`, «номер выборки деталей: целое больше

- **класс:** External interfaces. **origin:** source; отказ двойного старта и отбрасывание полей - derived.

### FR-2006 Строка MR

- **Требование:** строка MR показывает номер (GitHub `#N`, GitLab `!N`, D-02), название, автора (логин),

### FR-2009 Обновление вида MR/PR

- **Требование:** вкладка «MR/PR» показывает снимок и обновляет его по правилам FR-1006: открытие панели на вкладке и
  переход на неё выбирают заново, только если снимка нет либо он старше 5 минут; загруженный в проекте снимок
  обновляется в фоне по возрасту 5 минут, пока окно на виду; «Обновить» - внеочередной цикл с дебаунсом 300 мс, кнопка
  до ответа списка - «Обновление…» и недоступна (D-48 фичи 01). Выборка - в две фазы, пайплайн и апрувы приходят
  следом за списком (FR-2006). Без снимка - после смены фильтра, смены проекта, сохранения свойств проекта и до первого
  ответа - список показывается сразу после выборки списка со «…» в пайплайне и апрувах; при снимке на экране
  (фон, открытие, «Обновить») снимок держится до прихода деталей и заменяется списком с деталями целиком. Смена
  фильтра вытесняет идущую выборку; сортировка работает по снимку и во время выборки. Новая выборка детали прежней
  отбрасывает и её процессы CLI не прерывает (D-20). «Обновить» вдобавок проверяет вход заново (FR-1019).
- **traced from:** BR-2001.
- **источник:** цель, критерий 10; brief п.5 («при открытии вида и по кнопке, без фонового опроса») - заменён
  решением оператора 2026-10-27 (D-48 фичи 01); конвенция FR-1006; цель `panel-load-perf`, критерии 4, 5, 14; brief perf, «Требования» п.3.
- **rationale:** reason - бриф п.5; assumptions - показанный список - вид, готовый к работе; relationships -
  сценарий 5; design constraints - ADR-0008 п.8.
- **verification:** испытание - `test/flow.test.ts` (`RefreshGate`, «новая выборка во время деталей: детали
  прежней не применяются», «смена проекта до списка: ни списка, ни деталей», «канал списка MR получает recheck из
  триггера»), `test/mrs.test.ts` («список возвращается до деталей»); демонстрация - смена проекта.
- **класс:** Functions. **origin:** source; обновление при смене фильтра, D-20 и удержание снимка до деталей - derived.

### FR-2011 Сессия MR и её первое сообщение

- **Требование:** «Ревью» и «Доработать» открывают новую сессию Claude Code в репозитории проекта, remote которого
  дал MR, прочие репозитории проекта - дополнительными каталогами; remote MR у нескольких репозиториев - меню «Где
  открыть MR» с выбором репозитория. Первое сообщение сессии:
  - «Ревью» - `/dex-auto:auto review <URL MR>`;
  - «Доработать» - «Разбери замечания к MR <URL MR>: переключись на его ветку и доработай её по замечаниям ревью.»
  URL MR - `https://github.com/<owner>/<repo>/pull/<N>` либо `https://<хост>/<путь>/-/merge_requests/<N>` (D-08).
  Сообщение собирает главный процесс из проверенной ссылки на MR и намерения (FR-2016); название, ветки и автор MR в
  него не входят; оно передаётся `claude` первым позиционным аргументом без оболочки, до `--add-dir`. Ветку,
  checkout и worktree Cyborg не создаёт (FR-1016). Сессия, открытая из открытой панели, панель не закрывает и
  активной становится, только если активной не было (D-49 фичи 01).
- **traced from:** BR-2002.
- **источник:** цель, критерии 12-15, 20; brief п.6, п.9, «Старт сессии»; D-07, D-08.
- **rationale:** reason - бриф п.6; assumptions - D-07; relationships - сценарий 5; design constraints - ADR-0003
  п.9.
- **verification:** испытание - `test/mrs.test.ts` («mrPrompt», «mrUrl», «claudeArgs: промпт на «/» стоит до
  --add-dir»), `test/flow.test.ts` (`decideStart`); демонстрация.
- **класс:** Functions. **origin:** source.

## 14. Performance requirements

### NFR-2001 Предел деталей MR и процессов CLI

- **Требование:** пайплайн и апрувы PR GitHub запрашиваются не больше чем у 200 PR выборки - самых свежих по дате
  обновления после фильтра, по всем источникам GitHub вместе, - плюс MR с открытой сессией (не больше 200); у
  остальных - «—». У MR GitLab предела нет: детали всех открытых MR источника приходят запросом GraphQL (FR-2003).
  Вызовы деталей PR GitHub и MR с сессией вне списка делят один пул из 6 на все выборки, в том числе
  перекрывающиеся («Обновить», смена фильтра во время деталей), и задачи отброшенной выборки в очереди уступают
  задачам новой. Перекрывающиеся выборки без «Обновить» ждут GraphQL источника, уже идущий в полёте; «Обновить»
  запускает свой GraphQL и начатый до неё не прерывает (FR-2009), поэтому без «Обновить» процессов `gh`/`glab`
  одновременно не больше 6 + <число источников>, а каждое «Обновить» во время деталей добавляет по процессу GraphQL
  на источник GitLab, пока прежний не завершится. Пределы NFR-1003 действуют на каждый вызов.
- **traced from:** BR-2001; BRD фичи, открытый вопрос 1.
- **источник:** решение прогона (числа не из постановки): D-12, D-13; находки ревью F1, F2; цель `panel-load-perf`,
  критерий 8 и граница (пределы 200 и 6 не меняются), D-28.
- **rationale:** reason - детали PR стоят 2-3 вызова CLI, а лимит REST GitHub - 5000 запросов в час на
  пользователя, общий с видом задач; предел введён ценой REST-вызовов на MR и к GraphQL GitLab не применяется;
  assumptions - 200 свежих PR покрывают рабочий список; relationships - нет; design constraints - ADR-0008.
- **verification:** испытание - `test/mrs.test.ts` («процессов gh одновременно не больше пула плюс источники»,
  «детали - ровно у 200 самых свежих, у остальных «—»; MR с сессией получает детали», «страницы по курсору: предел
  200 не действует», «перекрывающиеся выборки во время деталей делят пул», «перекрывающиеся выборки GitLab делят
  один graphql», ««Обновить» во время graphql прежней выборки запускает свой запрос», `runLimited`).
- **класс:** Performance. **origin:** source.

### NFR-2002 Время загрузки вида MR/PR

- **Требование:** на проекте Upcore (3 репозитория GitLab на `git.dextechnology.com`) вкладка MR/PR показывает
  список не дольше 2 с, пайплайн и апрувы - не дольше 3 с, при открытии после проверки входа при старте и при
  «Обновить» с прежним результатом проверки (FR-1019). Открытие без прежнего результата и без проверки при старте
  предела не несёт и печатается справочно. Предел судится по медиане 5 прогонов замера.
- **traced from:** BR-2001.
- **источник:** brief perf, «Требования» п.2; цель `panel-load-perf`, критерии 3 и 22; D-31.
- **rationale:** reason - на Upcore вид открывался 8,3 с, 59 вызовов CLI, список показывался после всех деталей
  (brief perf, «Замер»); assumptions - пределы действуют и при первом открытии после запуска (цель, критерий 3);
  сценарии предела - решение владельца (D-31); relationships - FR-2006, FR-2009, NFR-1004; design constraints -
  ADR-0008, ADR-0009. Классификация данных и авторизация - раздел 18.
- **verification:** анализ - `npm run measure` (`scripts/measure.mjs`) на Upcore печатает время до списка MR и до
  деталей по сценариям «после проверки при старте», «Обновить» и справочную строку; замер владельца 2026-10-23
  (медиана из 5: список 0,79 / 1,26 с, детали 1,30 / 2,68 с) - D-31.
- **класс:** Performance. **origin:** source; сценарии суждения и медиана - решение владельца.
